Title: MMU030: a page descriptor root checks its limit with function code lookup too

When the root pointer is a page descriptor (DT = $1), `MMU030::walk` checks the root limit only if function code lookup (TC bit 24, FCL) is off. The root pointer register description says the check is made either way. For DT = $1: "A translation table for this root pointer does not exist. The MC68030 internally calculates an ATC entry (page descriptor) for accesses using this root pointer within the current page by adding (unsigned) the value in the table address field to the incoming logical address. This results in direct mapping with a constant offset (the table address). For this case, the processor performs a limit check, regardless of the state of the FCL bit in the TC register." [MC68030UM §9.7.1, p. 9-53](https://www.nxp.com/docs/en/reference-manual/MC68030UM.pdf#page=354)

The other mentions of the limit with FCL set are general rules: "when the FCL field of the TC register is set, the L/U and LIMIT fields of the root pointer registers are unused" [§9.5.1.2, p. 9-23](https://www.nxp.com/docs/en/reference-manual/MC68030UM.pdf#page=324). Also "In this case, the limit field of CRP or SRP is ignored" [§9.7.2, FCL, p. 9-55](https://www.nxp.com/docs/en/reference-manual/MC68030UM.pdf#page=356), and the root limit "applies when the function code lookup is not used" [§9.5.2, p. 9-32](https://www.nxp.com/docs/en/reference-manual/MC68030UM.pdf#page=333). They describe a root that points to a function code table, where the limit would have to apply to the function code ("the function code level cannot be limited", §9.7.1). A page descriptor root has no such table: the walk never uses the function code and goes straight to the TIA index. The DT = $1 sentence is the one written for this case, and it names FCL on purpose. §9.9.3.1 also presents early termination at the root as the way to get "a limit check on the range of physical addresses for the system" [p. 9-68](https://www.nxp.com/docs/en/reference-manual/MC68030UM.pdf#page=369).

**The manual is not consistent here, and you may prefer to keep master as it is.** In the detailed flowcharts, a DT = $1 root leaves the search as TYPE = 'EARLY' while y is still 'RP' ([Figure 9-25, p. 9-41](https://www.nxp.com/docs/en/reference-manual/MC68030UM.pdf#page=342)). ATC entry creation then calls the limit check ([Figure 9-27](https://www.nxp.com/docs/en/reference-manual/MC68030UM.pdf#page=343)), whose first branch is y = 'RP' and FCL = 1 → "limit check not required" ([Figure 9-28, p. 9-43](https://www.nxp.com/docs/en/reference-manual/MC68030UM.pdf#page=344)). That is what master does, and WinUAE does the same (`cpummu30.cpp`, `if (descr_num || !(tc_030&TC_ENABLE_FCL))`). Two points weigh against the figure:
- The same branch also skips the limit of an early-termination descriptor in the function code table, since y is still 'RP' there too. §9.5.1.1 says that limit "is still used as a check on the next index field of the logical address", and both Moira (`lookupLong`) and WinUAE (`descr_num`) check it. Neither of them follows Figure 9-28 literally.
- Figure 9-25 sets LAST_SIZE only on the table-root path, so Figure 9-28 tests a variable the DT = $1 path never set.

Both the second edition (1989) and the third edition linked here have the same §9.7.1 sentence and the same Figure 9-28. I have no capture from a real 68030. If you have one, or the MC68851 manual says otherwise, that should decide.

The patch removes the `if (!fcl)` around the DT = $1 check. The index is still `c.peekAddrBits()`, the TIA field after the initial shift: case 1 never consumes the function code. The same walk serves translation, PLOAD, PTEST and `peek()`. So with FCL on, an out-of-limit index now gives an ATC entry with B set (a bus error), and PTEST at level 1 to 7 sets L and I with N = 0, as §9.5.2 describes ("If a limit violation is detected during a table search for a PTEST instruction, the invalid (I) and limit (L) bits are set in the MMUSR").

The new unit test `Early Termination Limit` sets the CRP to a DT = $1 root at $20000 and the SRP to an unlimited DT = $1 root at 0, so the supervisor code is identity-mapped. It uses a 4K page and 10 + 10 index bits. With FCL off and on, and for an upper limit of 1 and a lower limit of 2, it checks an index just inside and one just outside the limit:
- `translate()` for user data gives $20000 + address, or fails;
- PTESTR #1,(A0),#7 gives MMUSR 0, or L|I ($4400) with N = 0;
- MOVES.L (A0),D0 with SFC = 1 reads the value, or takes a bus error.

On master it fails on exactly 8 assertions: the four checks of the FCL-on, outside-limit case, for each of the two limits. With the patch it passes.

RandomUAE compares PTEST and translation against UAE, which skips this check, so it found the new behaviour at once (seed 1, TC $81D06355, CRP $002A0001_00007A30, PTESTR at $AFA38000: UAE MMUSR $0000, Moira $4400). `randomTranslationSetup` now opens the limit of a DT = $1 root when it sets FCL. It draws no extra random numbers, so every other setup is unchanged, and FCL with a direct root is still translated and compared. If you would rather keep UAE as the reference here, this hunk is the one to drop together with the fix.

The unit suite (148 test cases) and the full ctest (26/26) pass on this branch.

Not covered: there is no hardware measurement. The tests check the limit only at the root with no initial shift. A PTEST at level 0 reports the B bit of the ATC entry, as before.

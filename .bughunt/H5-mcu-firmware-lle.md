### high — PIC1654S ADB clock divisor is hardcoded to the Mac II's 15.6672 MHz on every machine that instantiates `AdbVia`
- **Where:** `/home/gistarcade/src/POM68K/src/AdbVia.h:88` (used at `/home/gistarcade/src/POM68K/src/AdbVia.cpp:97,106-108`)
- **Defect:** `static constexpr int kCyclesPerPicInsn = 34` is 15667200/460800, but `AdbVia` is instantiated from 7.8336 MHz (`MacMemory`, SE/SE FDHD/Classic) to 33.33 MHz (`CentrisMemory::kCpuHzQ650`), so the transceiver firmware and every ADB bit cell it generates run at the wrong rate relative to guest time on all non-Mac-II machines.
- **Trigger:** Quadra 650 — `CentrisMemory.cpp:528 adbVia_.syncTo(cpu_->machineClock())` feeds 33 333 333 machine cycles/s into a divisor of 34, so the PIC executes at 980 kHz instead of 460.8 kHz (2.13× overclock) and the AdbLine bit cell (1564 units, `AdbLine.cpp:19-20` comment) lasts 47 µs instead of the ADB-spec 100 µs; the PIC firmware's inter-state timeouts therefore expire ~2× early against the ROM's ST/SR byte handshake — the exact failure mode documented at `AdbVia.cpp:99-105`. Mirror-image on Mac SE/SE FDHD/Classic (`MacMemory.cpp:86`, 7.8336 MHz, correct divisor 17): PIC at half speed, 200 µs bit cells. Also wrong: IIci (`RbvMemory.cpp:216`, 25 MHz → 54), Centris 610 (20 MHz → 43), Centris 650 / Quadra 610 / Quadra 700 (`Q700Memory.cpp:173`, 25 MHz → 54), Quadra 800 (33 MHz → 72). Same class as the recorded "bus time is not boosted" / "MCU LLE clock drift" traps; the sibling `CudaLle` already parameterises this (`CudaLle.cpp:194-196` with a ctor `cpuHz`), as does `CentrisMemory::viaDiv()`.
- **Fix:** make the divisor a machine parameter instead of a constant — add `int64_t cpuHz` to `AdbVia::attach()` and use a rational accumulator:
```cpp
picAcc_ += int64_t(cpuCycles) * 460800;
while (picAcc_ >= cpuHz_) {
    int cost = pic_.run(1);
    line_.tick(int(cost * cpuHz_ / 460800));
    picAcc_ -= int64_t(cost) * cpuHz_;
    pic_.setRtcc(line_.line());
}
```
Pass 15667200 from `MacIIMemory`, 7833600 from `MacMemory`, and `cpuHz_` from `CentrisMemory` / `Q700Memory` / `RbvMemory`.

### medium — `CudaLle::reset()` clears `pramInstalled_`, so a warm reset discards every PRAM byte the guest wrote since boot
- **Where:** `/home/gistarcade/src/POM68K/src/CudaLle.cpp:62`
- **Defect:** `reset()` sets `pramInstalled_ = false` without first copying the live MCU PRAM window (`$0100-$01FF`) back into `stagedPram_`, so `pram()` (`CudaLle.cpp:68-72`) reverts to the boot-time staged copy and the next PC3 release re-slaps that stale copy over the firmware's live PRAM (`CudaLle.cpp:151-157`).
- **Trigger:** Boot any LLE machine (default path). In the guest change anything held in XPRAM (monitor depth, volume, startup disk, AppleTalk, date/time) — the firmware stores it in its own RAM, never through `setPram`. Hit GUI Reset: `Cmd::HardReset → cpu.hardReset() → mem_.reset() → cudaLle_/egretLle_.reset()` (`Q605Memory.cpp:103`, `Q630Memory.cpp:105`, `V8Memory.cpp:149`, `SonoraMemory.cpp:95`, `VaspMemory.cpp:70`, `RbvMemory.cpp:139`). All settings revert. On the V8/Sonora/VASP/IIsi paths it is worse: those `reset()`s re-stage from the *HLE* `egret_.pram()` (`V8Memory.cpp:148-152` etc.), a copy that only ever receives live bytes in `savePram()`. Quitting between the reset and the next PC3 release persists the loss (`Q630Memory.h:132-136`). This contradicts the project's own stated contract for the same object: `Egret::reset()` deliberately preserves PRAM — `// seconds_/pram_ survive (battery-backed, like the Plus RTC)` (`Egret.cpp:126`) — and MAME's `cuda_device::device_reset()` never touches `m_pram_loaded` (cleared only in `nvram_default()`).
- **Fix:** snapshot the live window before dropping the flag (or, like MAME, do not drop it at all):
```cpp
if (pramInstalled_)
    for (int i = 0; i < 256; i++) stagedPram_[i] = mcu_.ramByte(0x100 + i);
// then leave pramInstalled_ alone, or clear it only when fresh NVRAM is staged
```

### low — `AdbVia::reset()` resets only the HLE half; the PIC core and the ADB wire survive a machine reset mid-transaction
- **Where:** `/home/gistarcade/src/POM68K/src/AdbVia.cpp:18-27`
- **Defect:** No `pic_.reset()`, no `line_.reset()`, no `picAcc_ = 0` — yet `attach()` performs exactly that for the LLE half right after calling `reset()` (`AdbVia.cpp:48`), so the two entry points leave the object in different states.
- **Trigger:** Hard reset on a Mac II/IIx/IIcx/IIci/SE/Quadra 700/Centris-Quadra 6x0/800 while an ADB transaction is in flight (autopoll runs continuously, so this is the common case): callers `MacMemory.cpp:64`, `MacIIMemory.cpp:88`, `CentrisMemory.cpp:73`, `RbvMemory.cpp:135`, `Q700Memory.cpp:71`. `pic_` keeps its PC, W, file registers and 2-level stack mid-routine; `line_` keeps `linestate_` mid-frame, an armed `sendTimer_`, `direction_`/`streamPtr_` mid-Listen and the previous boot's relocated `kbdAddr_`/`mouseAddr_`. `irqPending_` is forced false under a PIC whose RB4 latch still says asserted, so the VIA PB3 level only re-syncs on the PIC's next port-B write. The sibling firmware-LLE path does it correctly (`CudaLle.cpp:55-56` resets both `mcu_` and `adb_`); `Pic1654s::loadRom()` resets the core, which is why only `attach()` is currently clean.
- **Fix:** `if (lle_) { pic_.reset(); line_.reset(); picAcc_ = 0; }` at the end of `AdbVia::reset()` (leave `lastPicClock_` alone — the Moira clock is monotonic across `hardReset()`, so zeroing it would stall `syncTo`).

### low — inter-byte continuation threshold sits below the shortest pulse the PIC can emit, making the multi-byte Listen branch dead code
- **Where:** `/home/gistarcade/src/POM68K/src/AdbLine.cpp:95` (constant at `:25`)
- **Defect:** `else if (dtime < T_SYNC)` with `T_SYNC = 450` discriminates "another byte follows this even byte", but `dtime` there is the previous bit's *low* duration, which the PIC only ever emits as `kShort = 544` or `kLong = 1020` — the condition is unsatisfiable, so a Listen is hard-capped at 2 data bytes. MAME's identical test uses 90 ADB ticks (`macadb.cpp:978`), which sits *between* its short low (70 ticks) and long low (130 ticks); the POM68K equivalent is the same midpoint the file already defines, `T_BIT = 782`. The file's own header states the contract: "thresholds sit at the mid-points of its short/long pulses" (`AdbLine.cpp:17-18`).
- **Trigger:** Any Listen carrying more than two data bytes: after byte 2, `streamPtr_ == 2` is even, the branch cannot fire, the machine falls into `case LST_TSTOP:` and commits with `buffer_[0..1]` only; bytes 3+ are then re-decoded as a bogus command frame from `LST_IDLE`. Today only 2-byte Listens (R3 relocation) are exercised, so it is a latent divergence rather than a live regression.
- **Fix:** `else if (dtime < T_BIT) linestate_ = LST_BIT0;` (keep `T_SYNC = 450` for the `LST_ATTENTION` / `LST_RCVSTARTBIT` high-period checks). **This makes `buffer_[streamPtr_++] = command_` at `AdbLine.cpp:117` genuinely reachable past index 1, and `buffer_` is only 8 bytes (`AdbLine.h:86`, MAME uses 16) with no bound**, so bound it in the same patch: `if (streamPtr_ < int(sizeof buffer_)) buffer_[streamPtr_++] = command_;` — otherwise the overflow lands on `datasize_`, which then drives the send loop at `AdbLine.cpp:172/179/188`.

### low — keyboard Talk R3 returns the register-3 flags byte in the handler-ID slot
- **Where:** `/home/gistarcade/src/POM68K/src/AdbLine.cpp:290`
- **Defect:** `buffer_[0] = uint8_t(0x60 | kbdAddr_); buffer_[1] = kbdHandler_;` — `kbdHandler_` carries R3-*byte-0* semantics everywhere else in the file (initialised `0x22` = `0x20|addr2` at `:37`, SRQ-enable tested as `kbdHandler_ & 0x20` at `:269`, rewritten `(kbdHandler_ & 0xF0) | kbdAddr_` at `:310`), so it is being reported as the handler ID; the mouse branch six lines up has the correct layout (`buffer_[0] = mouseHandler_; buffer_[1] = 0x01;`, `:271`), as does MAME (`macadb.cpp:704-706 m_buffer[0] = m_keyboard_handler; m_buffer[1] = 0x01;`) and POM68K's own HLE `AdbBus.cpp:50`.
- **Trigger:** After ADBReInit the ADB Manager Talks R3 to address 2 and reads handler ID `$22`, which is not a defined keyboard handler ID, so keyboard-type detection sees an unknown device. Additionally, byte 0 is synthesized with bits 6 and 5 hard-set, so after a Listen R3 that clears the SRQ-enable bit (correctly applied to `kbdHandler_` at `:308` and honoured at `:269`), the readback still reports SRQ enabled. `tests/adbline_test.cpp` pins only the mouse form, so the divergence is untested.
- **Fix:** `buffer_[0] = kbdHandler_; buffer_[1] = 0x02; datasize_ = 2;` (byte 1 = handler ID; `0x01` to match MAME literally).

### low (latent) — M68HC05 one-second timer derives its period from the PLL selector while the integrator pins the core at a fixed 2.097152 MHz
- **Where:** `/home/gistarcade/src/POM68K/src/M68hc05.cpp:443-447`
- **Defect:** `cps = kPllHz[pllCtrl_ & 3] / 2` assumes the core's cycle rate follows the PLL, but `CudaLle` always clocks it at `kMcuHz = 2097152` (`CudaLle.h:82`, `CudaLle.cpp:194-196`), and the programmable timer twelve lines above assumes the opposite (fixed 512 cycles, `:434`). The two timers in the same loop use contradictory clock models; they agree only at PLL rate 3.
- **Trigger:** Any firmware that arms the one-second timer (`write8` `$12`, `:118-120`) before its first `$07` write, or that selects rate 0/1, gets `cps` = 262 144 / 524 288 while the core still executes 2 097 152 cycles per emulated second — the CPI heartbeat fires 8×/4× per second and the guest RTC runs 8×/4× fast, exactly the drift class recorded at `CudaLle.cpp:197-201` (boot gates miss it; only the soak gate catches it). Latent today: the `(v & 3) == 2 → v |= 3` rate-3 cheat at `M68hc05.cpp:106` pins every shipped Cuda/Egret dump to rate 3, where `cps` happens to equal `kMcuHz`.
- **Fix:** decouple it from the PLL selector the way MAME does (`m68hc05e1.cpp:199-203` arms the one-second timer with `attotime::from_seconds(1)` and scales only the prog timer): `const int64_t cps = 2097152;` — or, if the variable system clock is to be modelled, have `CudaLle` derive its MCU cycle rate from `mcu_.pll()` and scale the prog timer instead, so both timers share one clock model.

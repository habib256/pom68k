# CLAUDE.md

Always-loaded **orientation index**: it routes, it does not explain. The code
is the documentation; this file is the table of contents. Keep it scannable in
under a minute — anything that grows a paragraph belongs in `DEV.md` (how) or
`CHANGELOG.md` (why, dated).

POM68K's non-negotiable product scope is **every 68k Macintosh**. Its current,
expanding coverage is **37 machine profiles**, from the Mac
Plus (68000, cycle-exact) to the Quadra 950 tower (68040, functional), by way
of the PowerBook Duo 230 laptop, **every one booting the Finder**. 68k sibling
of [POMIIGS](../POMIIGS/) — same architecture, conventions and milestone
discipline; the CPU integration pattern (Moira wrapper) comes from
[NeoST](../neost/).

The profile list lives in **one** place: `kMachineProfiles` in
`src/MachineCatalog.h`, grouped by platform board. Each row carries the GUI
label/slug, runner kind, platform/CPU family, stable `SnapMachine` id, ROM
identity and variant environment. The GUI **Machine** menu and save-state
identity consume it directly. 37 profiles → 21 `MachineKind` values → **12
platform implementations** (the machine table below); this is current
coverage, not a product ceiling.

- All **37 profiles boot the Finder**, each covered by a boot-etalon gate
  (named per row in the machine table below). The OS-version sweep
  (System 4.1 → Mac OS 8.1) is `tests/finder_boot_matrix.cpp` — an on-demand
  harness, `EXCLUDE_FROM_ALL` and **not** a registered CTest. Bring-up
  history: `CHANGELOG.md`, by date.
- **227 CTest gates** (`ctest -N` 2026-08-22: 109 `unit`, 9 `smoke`, 40 `jit`,
  51 `m040`, 53 `m030`, 118 `etalon`, of which 12 `etalon-core` — one profile
  per platform, the pre-commit tier, 12/12 green in 31 min 41 s). The registry
  is **host-conditional by five**: the AArch64 lockstep trio (040 coarse,
  030 experimental, 030 alignment) is registered only on an AArch64 host
  with the native backends, and the x64 030 experimental + alignment
  locksteps only on x86-64 — so an x86-64 configure sees 224 and an
  AArch64 one 225.
  `docs_test` re-checks these totals — and every gate name this file spells
  out — against the roster CMake writes at configure time, and fails if any
  gate carries no label; since 2026-08-19 it also holds every in-tree
  `file:line` citation in the documentation set to its file's real length.
  The generated gate manifest also pins asset, host, scope and tier
  dimensions; `performance_budgets.tsv` pins policy by workload, guest
  family and host. Both native CI jobs publish the same
  `pom68k.jit.metrics.v1` artifact rather than reducing the proof to a CTest
  exit status.
- Last FULL run **222/222 green, 2026-08-18** — the whole registry on this
  host and the first one run in PARALLEL: 208 gates at `-j16` in 1 h 27 on
  the calibrated slot budgets, then the two families the RAM model cannot
  see (Q700/Eclipse, sharing `Q700Memory`, and the UDP-port AppleTalk gates)
  serialized in 43 min — 2 h 11 against the 4 h 30 sequential habit, on
  **relinked binaries**, freshness guard green before the tier
  (`CHANGELOG.md` 2026-08-18 (fourth)). Before it: 206/206 on 2026-08-16,
  4 h 30 sequential; the same tiers that morning were **102/112**, ten reds
  in five unrelated causes after nine days without a whole-suite run
  (`CHANGELOG.md` 2026-08-16).
  **The `make` is part of the claim, not a detail**: a run in early August
  returned 143/143 over binaries linked at *different times* — 102 of ~110
  older than `libpom68k_core.a` — and proved nothing, because `ctest` does
  not build. A phantom failure gets investigated; a phantom pass gets quoted.
  **A green `ctest` is only worth the freshness of its binaries.**
- **Read `drVolAtrb` bit 8 on a gate's disk image before theorising about its
  code.** The IIfx gates were red for two days and twice mis-diagnosed as a
  code regression; the cause was a boot volume with bit 8 clear (never
  cleanly unmounted) and in fact corrupted. Only the IIfx was affected because
  its ROM caps at System 7.6, so it is the one platform whose probe chain
  lists that image first. Image deleted, the gates fall back to
  `GISTPERSO-boot.vhd` — `CHANGELOG.md` 2026-08-06 (late night). The refusal
  underneath is CLOSED (2026-08-13 (seventh)): 7.6's dirty-volume path tears
  the video driver down mid-boot and `TobyVideo` swallowed its VBL disable —
  MAME-parity `vbl_w` fixed it, `iifx_persist_etalon` green. The method rule
  stands.
- **Every platform is GUI-complete**: 12 memory maps, 37 catalogue rows,
  37 `SnapMachine` tags, save states on all 12 families. Last to arrive: the
  Eclipse towers (Quadra 900/950, 2026-08-02, `docs/IOP_BRINGUP.md` § M7) and
  the **PowerBook Duo 230**, the first laptop (2026-08-06). The Duo's PRAM is
  the PG&E's own RAM+SRAM (`MscMemory::loadPram`, MAME's layout with the `$91`
  power-flag scrub — which `PgePmu::reset()` now needs too, or the mask ROM
  resumes into a STOP and never releases the 68030 again), not a discrete
  RTC. Its **keyboard matrix** and its **CPU power-down** (`power_cycle_w` — a
  stub until 2026-08-13, which froze the machine 58 s into an idle Finder)
  landed with the beyond-boot work, and its **trackball** on 2026-08-14
  (PG&E quadrature counters `$14`-`$16`, latched at 60 Hz — drained on read
  instead, half the directions vanish into a double-read race). Still open:
  the full sleep/wake gate no other machine can test (`docs/DUO_BRINGUP.md`,
  `TODO.md` § 7).
- **`docs/LLE_VS_HLE.md` lists no live BUG any more** (2026-08-02) —
  everything remaining in its § 1 is a *simplification*, each with its reason
  and its reopening condition. Since **2026-08-14** it also lists **no
  unconditional HLE**: the Eclipse towers were the last board running the
  command-level `Egret`, and now run the factory `341s0851` on a real
  68HC05 like every other Egret/Cuda machine (`q900_input_etalon`,
  `lle_a64_q900_preflight`). Every remaining HLE entry is a *fallback* — a
  missing dump or an explicit `*_LLE=0`, and never silent.
- **JIT**: `jit/auto` is the conformant default on 68040 **and, since
  2026-08-18, on 68030** — and since 2026-08-21 an 030 resolves to the
  NATIVE generator on **both** host ISAs. `auto` consults each backend's
  `caps().autoFamilies` SPEED declaration, separate from the
  `guestFamilies` correctness one; each (family, backend) pair entered on
  its own D.1 evidence: AArch64 on 2026-08-20 (score 64, −5.3 %), x86-64
  on 2026-08-21 (score 0, **−12.6 %** vs `threaded` at the bench's default
  budget, fp identical). The x64 flip had been blocked two days on **the
  four IIsi gates in SIGSEGV ~5 s in** under the generator — code the
  `jit_*` 030 gates had never run, since they pinned the engine, not the
  backend (`docs/JIT_BRINGUP.md` § C.4septies, now CLOSED: the crash did
  not survive the 2026-08-19→21 hardening; reproducer and triage order
  kept). `POM68K_JIT_BACKEND=x64|a64` selects generated code on
  an 030 explicitly, no unsafe override (the two 120k lockstep gates).
  68000/68020 stay opt-in; the interpreter remains the explicit accuracy
  oracle, with one `interp_*_boot_etalon` per 68030 platform as well.
- **040 caches: M0-M3 complete, 2026-08-16** (`docs/CACHE_040.md`): the
  opt-in architectural model carries I/D line data, WT/CB/NC policy, dirty
  writeback, CPUSH/CINV, snooping and hit/fill/push timing. Enable it with
  `POM68K_040_DCACHE=1`; product default waits on cache-aware JIT speed.
- Peripheral **event deadlines** are the default on eight platforms — V8,
  Sonora, VASP, RBV, Q605, Centris, Q700/Eclipse, Q630 — and **opt-in on two
  more** since 2026-08-13: Mac II family (`POM68K_MACII_EVENT=1`) and Duo
  (`POM68K_DUO_EVENT=1`), whose defaults stay the historical batch because
  the deadline measured **+14-17 %** and **+9 %** there for exactness no gate
  can see (`docs/LLE_VS_HLE.md` § 1.2 carries the numbers). The **IIfx is
  refused on evidence**: its IOPs execute continuously, so their bound is
  always 1. The compacts need none: `Cpu68k::sync()` calls `catchUp()` before
  **every** bus access, so their peripheral time is exact.
- **Release CI** ships four artifacts on tag (Linux x86_64/aarch64
  AppImage glibc-2.27, macOS Universal 2 dmg, Windows x64 zip);
  `--version` is the headless smoke. Bootstrap: run *Build bionic builder
  image* once, pin its digests in `release.yml`. Since 2026-08-08 the Linux
  two are built with **LTO** (it used to ride on `-march=native`, so every
  released binary had silently lost it) and the aarch64 one with
  `-mtune=cortex-a72` — ISA floor unchanged, so it still loads everywhere.
  A **fifth package is on demand**, `pi400.yml`: `-mcpu=<core>` (floor
  RAISED) as AppImage + tar.gz, no PGO possible in CI — `docs/RASPBERRY_PI.md`.

## Conventions (inherited from POMIIGS/POM2)

- **One concern per file** — each `.cpp/.h` pair owns one subsystem.
- **Every milestone is gated** by a CTest under `tests/` before the next
  depends on it.
- **`emuCycles` everywhere** — events carry CPU-cycle stamps, never wall-clock.
- **Docs in English**; conversation with the user may be French.
- **C++20** whole-tree (Moira requires it — divergence from POMIIGS's C++17).
- **License GPLv3**; ROMs are **user-provided, never committed**.

### Source of truth (ranked; cite file + line range in comments)

1. **MAME `mac.cpp` + `m68000` family** — primary hardware reference.
2. **Guide to the Macintosh Family Hardware** + *Inside Macintosh III* — docs.
3. **Hatari/WinUAE 68k timing** (via NeoST's convergence docs) — CPU timing.
4. **pce-macplus / minivmac / Basilisk II** — behavioural cross-checks.

## Build & run

```bash
./setup_imgui.sh             # one-time: fetches Dear ImGui + creates build/
cd build && cmake .. && make -j   # → build/POM68K + tests
ctest                        # 227 gates, ~4h (asset-dependent ones soft-skip)
ctest -L unit                # 109 legacy non-etalon gates
ctest -L asset-none          # 83 gates — manifest-declared asset-free tier
ctest -L smoke               # 9 gates — one machine, both CPU engines
ctest -L etalon-core         # 12 gates — ONE profile per platform, 31 min
ctest -L jit                 # 40 gates;  -L m040 = 51;  -L m030 = 53
make -j4 jitdev && ctest -L smoke   # the JIT working loop
cmake --build . -j4 --target jitfast && POM68K_JIT_REQUIRE_NATIVE=1 ctest -L jit-fast
./POM68K [ROM] [media...]    # profile picked by ROM size + checksum; the
                             # mapping is kMachineProfiles in MachineCatalog.h

tools/pgo_train.sh build-pgo # PGO here (train + rebuild, ONE build dir)
packaging/raspberry/build_native_pi.sh --pgo   # PGO + LTO + -mcpu, on a Pi
```

Three optimization knobs, **independent since 2026-08-08** (they used to be
one, which cost every released binary its LTO): `POM68K_NATIVE` (native ISA,
ON), `POM68K_TUNE=<core>` (schedule for a core, ISA floor unchanged — the
release aarch64 AppImage uses `cortex-a72`), `POM68K_LTO` (**ON since
2026-08-17**; it defaulted to `POM68K_NATIVE` until then, so the split was
only half done — a distributable build sets NATIVE=OFF and still lost LTO
unless it asked twice). Turning LTO off is now a stated choice: the CI
`linux` job and both macOS packaging paths pass `-DPOM68K_LTO=OFF` with a
reason. Numbers, provenance and the silent-PGO trap: `docs/RASPBERRY_PI.md`.

**A full run is 4 h 30 only because it is run sequentially**, and that is an
invocation habit, not a constraint: there is no `RUN_SERIAL` and no
`RESOURCE_LOCK` in the tree, and `ScsiDisk::open()` loads images with
write-back off, so gates are readers of the shared assets. What a gate costs
now lives in `gate_resource_budgets.tsv` (per host, same shape as
`performance_budgets.tsv`); CMake turns it into `PROCESSORS`, and the gate
manifest's `slots_src` says `measured` or `assumed`. **The etalon tier is
calibrated on x86-64 since 2026-08-18** (102 of its 118 gates `measured`,
16 still `assumed`; 83 gates cost more than one 256 MiB slot, the largest
30) — every other host is uncalibrated: sweep it with
`tools/measure_gate_ram.py -L etalon --fail-on-skip` where the images
live. Measured on x86-64: the asset-free tiers fit in one 256 MiB slot
each; `asset-none` 3.08 s → 0.80 s at `-j4`, `unit` 9.45 s → 5.32 s,
verdicts identical.

Never iterate on a full `ctest` or a full `make` — labels are derived from
test names at the end of `CMakeLists.txt`; pick the narrowest tier.

Clocks/video per machine live in the machine's `*Memory` ctor (`cpuHz`), not
here. Anchors worth remembering: Mac Plus **7.8336 MHz**, 60.15 Hz
(130 240 cycles/frame), 512×342×1 bpp (MSB = leftmost, 1 = black); LC II
**15.6672 MHz**; Quadra 605 **25 MHz**, 640×480×8. Quadra CPU default is
68040 + its own FPU (`FPUModel::M68040`); `POM68K_Q605_NOFPU=1` → 68LC040 + soft 68882, `=2` → true
bare `FPUModel::NONE` — both reach the Finder (integer PACK 4 via the XPRAM
`$AE` ROM-resource combo).

Mac Plus 24-bit address map, boot overlay, framebuffer/sound-buffer offsets
and the contention model: `DEV.md` § 2.1. Every other map is
in its `*Memory.h`.

## CPU core: Moira (permanent fork)

`extern/moira/` came from NeoST (itself Dirk Hoffmann's Moira, MIT), NeoST's
patches included. **Since 2026-08-09 it is a fork, not a vendored library**:
29 patch groups, 392 marked lines, 82 `pom*` extension identifiers — a re-sync would be a port,
so upstream is cherry-picked deliberately, never merged. The decision, its
rejected alternative and its reopening condition are the first section of
`extern/moira/POM68K_VENDOR.md`, which also carries every local change.
Config: `MOIRA_PRECISE_TIMING`,
`MOIRA_EMULATE_ADDRESS_ERROR`, no Musashi mimicry. Executes 68000/68010
cycle-exact, and 68020 / **68030 + PMMU** / **68040 + 68LC040 + 040 MMU**
functionally.

The 030/040 extensions were built from the Motorola manuals with AI +
differential fuzzing against the vendored **WinUAE/Hatari oracle**. **On
spec/oracle conflict, the oracle wins.** The 040 path has an ATC fast path and
a throughput/i-cache overlay (`POM68K_Q605_CACHE_BOOST`, default **4**; the
old boost-1 pin was a stale SCSI symptom), plus the opt-in architectural I/D
cache model described above. Native code is line-residency guarded and
all native data accesses cross the architectural D-cache.
Bus timing is counted on **machine** cycles, never on the boosted clock.
On the three boards that pair a boosted 030 with `Swim1` — V8, VASP, RBV
(`Cpu030`, `VaspCpu`, `RbvCpu`) — the boost **freezes to 1 while the floppy
motor runs** (Apple's denibble path is hand-timed to the IWM's 14-tick hold;
`POM68K_FLOPPY_BOOST_GATE=0` reproduces the old GCR-mount refusal —
`CHANGELOG.md` 2026-08-05 (eighth)/(ninth)).
